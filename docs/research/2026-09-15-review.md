## Where I agree

- Use real MuJoCo physics and two real SO-101 model instances.
- Separate the AI, motor controller, simulator, success checks and recovery.
- Start with a scripted controller to check the robot and generate examples.
- Let the AI suggest actions; check the actions and physical outcomes separately.
- Keep camera/state/language inputs separate from exact simulator object data.
- Save seeds, versions, failures, actions and outcomes for repeatable evaluation.

## Where I push back

1. **The package-rescue task misses the supplied challenge.** Preserve the
   recovery idea, but apply it to setting a dinner table. Begin with one simple
   action, then extend it to the required multi-step workflow.
2. **OpenVINO is not a stretch goal here.** The supplied brief assigns Intel
   optimization 20 points and requires a benchmark. Select a model with a
   practical export path early. A fast unrelated toy model is not evidence of
   faster robotics inference.
3. **Simulation-only does not mean any final computer is allowed.** The brief
   says no physical SO-101 arms are needed. Separately, it requires final
   simulation and inference on Core Ultra Series 2/3. The earlier platform
   section is looser; clarify with organizers if necessary.
4. **SmolVLA is a candidate, not a ready-trained two-arm solution.** Its official
   guide recommends about 50 demonstrations as a starting point. Its roughly
   four-hour A100 example for 20,000 steps is not a timing promise for our task.
   Camera names, joint order, action units and training data must match.
5. **ACT is an allowed alternative in the brief.** It may be simpler to export,
   but plain ACT does not automatically provide language understanding. Any
   language/vision task layer and policy conditioning must be explicit.
6. **Basic checks should start immediately.** Reject invalid numbers, stale
   commands, wrong arm names and joint-limit violations before driving motors.
   Check physical contacts during stepping too. This is not a formal safety proof.
7. **Physical success must be stricter than a pretty video.** Require real
   contact, stable supported placement, release and meaningful participation by
   both arms. Never teleport the object or secretly attach it to a gripper.
8. **Make recovery comparisons fair.** Use matching seeds, perturbations and time
   budgets. Report both event counts and episode outcomes with clear denominators.
9. **Do not install the whole Intel stack on this Windows laptop.** The linked
   guide targets Ubuntu and suitable Intel devices. Reuse relevant model tools
   and keep a separate deployment setup for the final target machine.

## Model and simulation choice

Use Google DeepMind Menagerie's robotstudio_so101, preserving its Apache-2.0
license and exact revision. This includes actual SO-101 joint names, gripper
collision shapes and a wrist camera. Do not substitute an invented robot.

MuJoCo's official changelog confirms version 3.13.0 on September 8, 2026.
The existing environment has 3.13.0, but its native Windows library fails to
load with WinError 1114, including outside the sandbox. This must be resolved
before claiming a working simulation. The environment uses Anaconda Python
3.12.4; the precise cause of the library failure is still being checked.

First checkpoint: compose two named arms, validate commands, render cameras,
check repeatable reset and save actual motion evidence. This is a control check,
not task completion. Next: a contact-based table-item grasp/release, then a
complementary two-arm task, demonstrations, learned actions and Intel deployment.
